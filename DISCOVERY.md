## Versions and provider contracts

Live registry responses: [azuredevops](https://registry.terraform.io/v1/providers/microsoft/azuredevops) **1.16.0** (current major 1), [azuread](https://registry.terraform.io/v1/providers/hashicorp/azuread) **3.10.0**, [azurerm](https://registry.terraform.io/v1/providers/hashicorp/azurerm) **5.9.0**. Latest AzureRM 4.x is **4.81.0**. Pin azuredevops exactly to 1.16.0 and azuread exactly to 3.10.0 for a reproducible verified contract. The root needs no AzureRM provider; examples pin 4.81.0 for compatibility with the existing Key Vault module's `< 5.0.0` requirement. No assumption that Azure DevOps follows AzureRM versioning.

- [Project 1.16.0](https://github.com/microsoft/terraform-provider-azuredevops/blob/v1.16.0/website/docs/r/project.html.markdown): required name; optional description, visibility (private/public, default private), version_control (Git/Tfvc), work_item_template (Agile/Basic/CMMI/Scrum or existing custom template), features (boards/repositories/pipelines/testplans/artifacts enabled/disabled). Organization must already exist; provider org_service_url identifies it. Organization creation is outside this provider's resource model.
- [ARM service endpoint 1.16.0](https://github.com/microsoft/terraform-provider-azuredevops/blob/v1.16.0/website/docs/r/serviceendpoint_azurerm.html.markdown): same resource, with service_endpoint_authentication_scheme = WorkloadIdentityFederation. Required project_id, service_endpoint_name and azurerm_spn_tenantid; subscription ID/name supplied for subscription scope. credentials.serviceprincipalid sets manual identity composition; no serviceprincipalkey or certificate. Exported workload_identity_federation_issuer/subject come from Azure DevOps, not string interpolation. features.validate defaults false, allowing trust creation after endpoint creation without a dependency cycle. The docs' private-preview note is stale relative to Microsoft's GA documentation.
- [Variable group 1.16.0](https://github.com/microsoft/terraform-provider-azuredevops/blob/v1.16.0/website/docs/r/variable_group.html.markdown): project_id, name, at least one variable block; allow_access configurable (source schema optional/default false despite prose saying required). Optional key_vault { name, service_endpoint_id, search_depth }. Linked variables have name only; value/is_secret/secret_value conflict with key_vault. Provider queries secret metadata through the service endpoint and fails if named enabled secrets do not exist. Plain groups support key/value entries; this module deliberately routes sensitive values through Key Vault rather than accepting secret values in Terraform.
- [Application 3.10.0](https://github.com/hashicorp/terraform-provider-azuread/blob/v3.10.0/docs/resources/application.md): required display_name; optional owners/sign_in_audience. Set AzureADMyOrg and explicit owners; no password block.
- [Service principal 3.10.0](https://github.com/hashicorp/terraform-provider-azuread/blob/v3.10.0/docs/resources/service_principal.md): required client_id, optional owners. OwnedBy automation needs ownership on both app and SP.
- [Federated credential 3.10.0](https://github.com/hashicorp/terraform-provider-azuread/blob/v3.10.0/docs/resources/application_federated_identity_credential.md): required application_id (resource ID, not client ID), display_name, audiences, issuer, subject. Audience api://AzureADTokenExchange. Chain: application → SP → manual WIF endpoint → app federated credential. Variable groups wait for the credential.
- [Role assignment 4.81.0](https://github.com/hashicorp/terraform-provider-azurerm/blob/v4.81.0/website/docs/r/role_assignment.html.markdown): scope and principal_id required; role_definition_name or role_definition_id required. Existing FK RBAC composition is sufficient; no reason to duplicate it.
- [Pipeline definition 1.16.0](https://github.com/microsoft/terraform-provider-azuredevops/blob/v1.16.0/website/docs/r/build_definition.html.markdown): repository YAML path points at delivery logic for YAML pipelines. The provider also exposes classic-pipeline jobs, which are a different surface and remain out of scope. The sibling terraform-az-fk-devops-pipeline owns this definition; no stage/job/step graph is modeled here.

## Azure DevOps-specific OIDC claims

[Microsoft's current troubleshooting table](https://learn.microsoft.com/en-us/azure/devops/pipelines/release/troubleshoot-workload-identity?view=azure-devops) distinguishes:

| Issuer family | Issuer | Subject |
|---|---|---|
| Azure DevOps | https://vstoken.dev.azure.com/{organization-id} | sc://{organization-name}/{project-name}/{service-connection-name} |
| Microsoft Entra | https://login.microsoftonline.com/{tenant-id}/v2.0 | {entra-prefix}/sc/{organization-id}/{service-connection-id} |

[Current manual configuration guidance](https://learn.microsoft.com/en-us/azure/devops/pipelines/release/configure-workload-identity?view=azure-devops) says new connections use Entra issuer by default and eligible public-cloud single-tenant legacy issuers retire July 1, 2027. Therefore use the endpoint's returned issuer/subject without hardcoding either format. Provider 1.16.0 source reads both from authorization parameters returned by the API. It has no explicit issuer-family selector. No real-organization apply is authorized, so actual issuer selection and runtime authentication are not claimed tested. Do not copy GitHub's repo: subject claims. Renames/conversion require reconciling exact claims in the federated credential.

## Key Vault and prerequisites

[Microsoft's variable-group guidance](https://learn.microsoft.com/en-us/azure/devops/pipelines/library/link-variable-groups-to-key-vaults?view=azure-devops) confirms secret-name mappings, Get/List permissions, public-endpoint RBAC support and private-endpoint RBAC restrictions. Example 02 uses the existing Key Vault module with access policies and public endpoint access; it accepts externally populated secret names and creates no secret values. Creating a new vault and populating it before linking is necessarily a documented staged workflow, since provider creation validates that secrets already exist.

Existing organization, organization administration/library/endpoint permissions, an Azure subscription, Entra application-management rights and external RBAC assignment permissions are prerequisites. Bootstrap provider authentication is separate from the pipeline's passwordless service connection. No organization, standalone repository, pipeline definition/YAML, networking, resource group or deployment target belongs to this root module. Azure may provision default project contents as part of project creation.
